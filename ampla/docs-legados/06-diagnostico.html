06 — Diagnóstico & Plano ​

Documento original

Conteúdo integral preservado de docs/06-diagnostico-e-plano-de-engenharia.md. Parte da wiki para manter a rastreabilidade com a documentação histórica do projeto.

Status: Análise Diagnóstica e Roadmap de Refatoração
Objetivo: Elevar o sistema de "Protótipo Avançado (Mockado)" para "Sistema em Produção 100% Funcional e Integrado".

1. Visão Geral do Diagnóstico ​

O sistema Ampla Vendas ERP atualmente possui uma excelente base de UI (React + Tailwind) e uma fundação conceitual forte para resiliência offline usando Dexie.js (IndexedDB). No entanto, uma análise profunda do código atual revela débitos técnicos significativos e gaps arquiteturais que caracterizam o sistema atual como um protótipo avançado, não pronto para produção.

Se colocado em produção no estado atual, o sistema apresentará problemas graves de escalabilidade de código, dessincronização de dados mestre e perda de pedidos em cenários de fechamento abrupto da aplicação.

Mudanças estruturais serão necessárias.

2. Erros Fundamentais e Débitos Técnicos Identificados ​

2.1. Inbound Sync (Carga de Dados Mestre) Inexistente ​

  • O Problema (Erro Crasso): O banco local (src/db/db.ts) está sendo populado com dados falsos (mocks locais via função seedDatabase). Não existe rotina para baixar o catálogo real de Produtos, Clientes e Condições de Pagamento do Supabase para o IndexedDB local.
  • Impacto no Negócio: O vendedor nunca verá novos produtos, alterações de preços ou atualizações nos limites de crédito dos clientes.
  • Ação Corretiva: Substituir o seedDatabase mockado por rotinas reais de Pull/Fetch da API REST do Supabase (pullClients, pullProducts), salvando-os no Dexie.js de forma assíncrona.

2.2. O "Adapter via Microserviço" é apenas Teórico ​

  • O Problema: A documentação cita um Middleware/Adapter para integração com ERPs (SAP/TOTVS), mas no código há apenas o envio direto da PWA para o Supabase (syncOrderToSupabase). O Supabase atua apenas como banco, não como integrador.
  • Impacto no Negócio: Pedidos chegam no Supabase, mas nunca chegarão ao ERP do cliente.
  • Ação Corretiva: É necessária a implantação de um backend (ex: Supabase Edge Functions em Deno/TypeScript ou um Server Node.js) que "escute" as inserções no Supabase e converta o Payload Canônico em requisições específicas (SOAP/OData/REST) para o ERP do cliente.

2.3. Sincronização Outbound Assíncrona Ingênua ​

  • O Problema: A sincronização para a nuvem depende que a aba do navegador esteja aberta e que o usuário ou um loop simples dispare a função.
  • Impacto no Negócio: Se o usuário cria um pedido no modo avião e, logo depois, fecha o aplicativo, o pedido ficará preso no celular infinitamente até o app ser reaberto, podendo causar perda de faturamento.
  • Ação Corretiva: Implementar Service Workers com a API de Background Sync e arquitetura de Fila Outbox real no Dexie.js.

2.4. Arquitetura Monolítica de Estado no Frontend (App.tsx) ​

  • O Problema: O arquivo principal App.tsx possui cerca de 400 linhas e atua como um "God Object", controlando quase todos os estados globais (abas ativas, listas de dados, modais abertos).
  • Impacto Técnico: À medida que o sistema crescer, o prop drilling (passar propriedades dezenas de níveis para baixo) tornará a manutenção lenta e dolorosa.
  • Ação Corretiva: Implantar uma biblioteca de gerenciamento de estado global (como Zustand ou React Context API) para abstrair a lógica de negócio para fora da camada visual.

3. Plano de Engenharia e Implantação (Roadmap 4 Sprints) ​

Este roadmap define as intervenções diretas na base de código para evoluir o sistema.

Sprint 1: Fundação e Sincronização Reversa (Inbound) ​

  1. Remoção de Mocks: Eliminar dados falsos do src/db/db.ts.
  2. Setup Supabase Completo: Implantar as tabelas descritas no Script DDL dentro de um projeto real Supabase.
  3. Inbound Sync Layer: Criar arquivo src/lib/syncEngine.ts contendo funções para fazer download (SELECT) de produtos, clientes e condicoes_pagamento do Supabase e fazer o Upsert (inserção/atualização) local no Dexie.js.
  4. Login Real: Substituir a verificação estática de PIN em UserProfilesManager.tsx pelo Supabase Auth (JWT Tokens).

Sprint 2: Roteamento, Segurança e Arquitetura de Estado (UI/UX) ​

  1. Roteamento Seguro (react-router-dom): Substituir a navegação por estado no App.tsx por rotas reais.
  2. Separação de Contextos & Auth Guards: Criar rotas abertas para o App (/) e proteger a documentação estratégica (/docs) usando Google OAuth ou Supabase Auth.
  3. Lazy Loading e Chunking: Garantir que o código sensível da documentação e painéis administrativos só sejam trafegados para usuários logados e autorizados.
  4. Desacoplamento de App.tsx: Criar uma store Zustand (ex: useAppStore.ts) contendo variáveis de controle globais (usuário logado, aba ativa, status de conexão).

Sprint 3: Robustez Offline e Fila de Sincronização (Outbox) ​

  1. Configuração de PWA Completo: Configurar vite-plugin-pwa para gerar o arquivo de manifesto real (manifest.json) e instalar o aplicativo.
  2. Service Worker de Fila: Criar um script rodando no fundo que detecta o evento window.addEventListener('online') e varre a tabela orders do Dexie.js onde statusSync === 'pendente_sync', enviando-os lote a lote.

Sprint 4: Middleware e Integração ERP Legado (Adapters) ​

  1. Edge Functions Supabase: Codificar uma Edge Function (Deno) para ser o gatilho (Trigger) quando um novo registro entrar na tabela pedidos.
  2. Roteamento Canônico: A Edge Function disparará requisições formatadas (XML ou JSON complexo) para os IPs externos dos ERPs (Protheus, SAP, etc).
  3. Gerenciamento de DLQ (Falhas): Se o ERP recusar o pedido (ex: Cliente Bloqueado), o Supabase retornará via WebSocket a rejeição para o celular do vendedor, atualizando o pedido para status_sync = 'erro'.

4. Conclusão da Análise ​

O estado atual da base de código possui um excelente Design System (Tailwind) e uma prova de conceito de banco de dados offline sólida (Dexie). No entanto, para ser considerado um produto B2B final 100% funcional, a barreira dos "dados falsos" deve ser rompida.

Implementar a comunicação bidirecional real com o Supabase e adotar um estado global robusto (Zustand) são as premissas inegociáveis para o próximo estágio do projeto. As mudanças não destruirão o que foi feito em nível visual, mas alterarão drasticamente o núcleo lógico de roteamento de dados.
