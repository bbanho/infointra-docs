08 — Sincronização Offline ​

Documento original

Conteúdo integral preservado de docs/08-estrategia-sincronizacao-offline.md. Parte da wiki para manter a rastreabilidade com a documentação histórica do projeto.

1. Visão Geral ​

Como parte da filosofia de engenharia orientada aos negócios da Axio, o ERP Ampla Vendas opera primordialmente de forma Offline-First. Isso garante que vendedores e representantes possam continuar faturando e emitindo pedidos mesmo em regiões sem conectividade (0% de sinal 4G/Wi-Fi).

Esta abordagem introduz complexidade arquitetural que foi calculada e justificada pela disponibilidade ininterrupta das operações comerciais.

2. Padrão Outbox e Conexão Zero ​

Para mitigar a complexidade de requisições HTTP falhas quando não há conexão:

  • Zero Conexão: Quando o usuário está offline, não disparamos requests HTTP diretos que fatalmente falhariam (gerando unhandled rejections).
  • Padrão Outbox (Caixa de Saída): Toda "mutação" (ex: criar pedido, atualizar cliente) é interceptada pela camada de serviço e gravada localmente (IndexedDB via Dexie.js) em uma fila cronológica (outbox_sync_queue).
  • Sync em Background: Um Service Worker ou um loop de checagem de conectividade observa o estado da rede. Assim que a conexão é restaurada, a fila é processada sequencialmente, garantindo a consistência das transações no backend.

3. Empacotamento do Estado Local (Cache) ​

A operação offline exige um repositório de dados cliente.

  • O cache não é apenas para leitura rápida (como o cache do navegador tradicional), mas um banco de dados relacional embarcado no browser (IndexedDB abstrato pelo Dexie.js).
  • Snapshot Local: Durante o primeiro login ou sincronização de "bom dia", o app faz o download (paginado/compactado) do catálogo de produtos, tabela de preços e carteira de clientes, empacotando o "Estado Offline".

4. Resolução de Conflitos (Event Sourcing & Timeline) ​

Operações distribuídas podem gerar "colisões", análogas ao git cherry-pick ou merge conflict.

  • Decisões "Forkadas": Se dois vendedores offline atualizam o mesmo registro (ex: alteram o telefone de um cliente), cada um cria um fork temporário em suas timelines locais.
  • Tipos de Colisão:
    • Soft (Cadastros/Metadados): Resolução baseada em Last-Write-Wins (Última gravação vence), calculada com base no timestamp da mutação local.
    • Hard (Estoque/Financeiro): Em vez de sobrescrever o saldo (ex: estoque local = 5), gravamos a Intenção/Evento (ex: -1 item A). Ao chegar no servidor, o evento é aplicado na timeline real. Se o saldo servidor já for insuficiente (estoque = 0), a operação entra em estado de "Alerta/Pendente" para aprovação gerencial, não abortando silenciosamente a venda, mas garantindo que o furo de estoque seja tratado.
  • Isso é conhecido como modelagem de Timeline Baseada em Eventos, essencial para a arquitetura de sincronização do Axio.

5. Reversibilidade e Flexibilidade (Cloud-Only) ​

Se os requisitos de negócios mudarem no futuro e a exigência de "local-first" for descartada em favor de uma versão estritamente online:

  • A arquitetura está preparada para uma migração de baixo esforço (Patch/Bypass).
  • Como as regras de negócio e a interface não sabem que o Dexie existe (elas conversam com um "Adapter/Repository" de dados), basta trocar a injeção de dependência do OfflineRepository para um CloudRepository (que faz o request HTTP direto para o Supabase/Edge Functions).
  • A base de UI (React) e regras de estado global (Zustand) permaneceriam 100% inalteradas.
