Autenticação & Identidade (Supabase Auth) ​

Decisão de arquitetura: o login é concentrado no Supabase Auth — hub de identidade único do sistema. Além de email/senha, o Supabase oferece OAuth (Google, GitHub, etc.) que outros serviços (ERP adapters, dashboards, integrações) poderão consumir com o mesmo token.

Estado atual do código (protótipo) ​

O LoginScreen.tsx implementa um fluxo em camadas, com fallback para funcionar 100% offline:

CamadaMecanismoPapel
1. Supabase AuthsignInWithPassword(email, pin) + consulta à tabela vendedoresLogin real quando há credenciais e conexão
2. Fallback offlineDEFAULT_USER_PROFILES (db.ts) comparando email + pinSegurancaOperação em campo sem rede
3. Auth dos docsloginForDocs() no store: email @axio.eng.br + senha ampla2026Protege a rota /docs (capital intelectual) — mock, não produção

Direção (em andamento) ​

  1. Concentrar tudo no Supabase Auth — o fallback local e o mock dos docs devem dar lugar ao Supabase como única fonte de identidade.
  2. OAuth para outros serviços — o Supabase (GoTrue) fornece providers OAuth; o mesmo JWT autentica o app, os adapters ERP e futuras integrações.
  3. Perfis em vendedores — já existe a consulta por email após signInWithPassword; a tabela precisa ser populada via Supabase Auth (User → vendedor).

Notas de segurança ​

  • PINs em texto plano nos DEFAULT_USER_PROFILES são aceitáveis só para demo — em produção os vendedores são usuários Supabase Auth com senha hasheada.
  • O mock ampla2026 para /docs protege o protótipo, mas não é segurança real — com o Supabase Auth consolidado, a rota deve exigir sessão válida (auth.getUser()).
  • RLS com auth.uid() já é a base para restringir dados por vendedor (docs/07).
