Modelo de Dados & Supabase ​

Backend relacional ​

O backend é o Supabase Cloud (PostgreSQL gerenciado + PostgREST). O DDL completo é gerado por generateSupabaseSqlSchema() em src/utils/supabaseAndFiscal.ts e pode ser executado no SQL Editor do painel Supabase.

As 5 tabelas fundamentais ​

sql
-- 1. CLIENTES (PF e PJ)
CREATE TABLE public.clientes (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  tipo VARCHAR(10) NOT NULL CHECK (tipo IN ('PF','PJ')),
  razao_social VARCHAR(255) NOT NULL,
  cpf_cnpj VARCHAR(20) NOT NULL UNIQUE,
  limite_credito NUMERIC(12,2) DEFAULT 0.00,
  credito_utilizado NUMERIC(12,2) DEFAULT 0.00,
  status VARCHAR(20) DEFAULT 'ATIVO'
    CHECK (status IN ('ATIVO','BLOQUEADO','INADIMPLENTE')),
  -- + endereço completo (logradouro, cep, cidade, uf) para cálculo fiscal
);

-- 2. PRODUTOS / SERVIÇOS (catálogo + estoque)
CREATE TABLE public.produtos (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku VARCHAR(50) NOT NULL UNIQUE,
  nome VARCHAR(255) NOT NULL,
  categoria VARCHAR(100) NOT NULL,
  is_service BOOLEAN DEFAULT FALSE,
  preco NUMERIC(12,2) NOT NULL DEFAULT 0.00,
  estoque_atual INT DEFAULT 0,
  -- NCM para emissão fiscal
);

-- 3. CONDIÇÕES DE PAGAMENTO
CREATE TABLE public.condicoes_pagamento (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  codigo VARCHAR(50) NOT NULL UNIQUE,  -- PIX, BOLETO_30, FATURADO_ERP...
  descricao VARCHAR(255) NOT NULL,
  parcelas INT NOT NULL DEFAULT 1
);

-- 4. PEDIDOS (mestre)
CREATE TABLE public.pedidos (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  codigo_pedido VARCHAR(50) NOT NULL UNIQUE,
  vendedor_id VARCHAR(50) NOT NULL,
  cliente_id BIGINT REFERENCES public.clientes(id) ON DELETE SET NULL,
  total NUMERIC(12,2) NOT NULL DEFAULT 0.00,
  status_sync VARCHAR(30) DEFAULT 'sincronizado',
  status_fiscal VARCHAR(30) DEFAULT 'PENDENTE'
    CHECK (status_fiscal IN ('PENDENTE','NFE_EMITIDA','CUPOM_EMITIDO')),
  chave_nfe VARCHAR(50), protocolo_nfe VARCHAR(100), cupom_fiscal_numero VARCHAR(50),
  assinatura_base64 TEXT, xml_gerado TEXT
);

-- 5. ITENS DO PEDIDO (relacional 1:N com cascata)
CREATE TABLE public.pedido_itens (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  pedido_id BIGINT NOT NULL REFERENCES public.pedidos(id) ON DELETE CASCADE,
  produto_id BIGINT REFERENCES public.produtos(id) ON DELETE SET NULL,
  sku VARCHAR(50) NOT NULL,
  preco_unitario NUMERIC(12,2) NOT NULL,
  quantidade INT NOT NULL
);

Cliente Supabase (lazy singleton) ​

Arquivo: src/lib/supabase.ts

  • Credenciais: env vars VITE_SUPABASE_URL / VITE_SUPABASE_ANON_KEY ou configuradas pelo usuário no front (localStorage) via SupabasePrepSection.
  • getSupabaseClient(): inicialização lazy — só cria a instância quando há credenciais válidas; retorna null e o app continua 100% local se não configurado.
  • testSupabaseConnection(): valida URL/chave com uma contagem na tabela produtos (tolerante a PGRST116 = tabela ainda não criada).

Sincronização de pedidos (upsert idempotente) ​

syncOrderToSupabase() (src/lib/supabase.ts:104):

  1. Upsert do cabeçalho em pedidos com conflito em codigo_pedido → reenvio não duplica.
  2. Busca o id retornado (parentId).
  3. Limpa itens antigos do pedido (delete().eq('pedido_id', parentId)) e reinsere — atualização atômica de itens.
  4. Retorna { success, message } — a UI mostra o resultado e registra em syncLogs.

syncClientToSupabase(): mesmo padrão com upsert em cpf_cnpj.

Row Level Security (RLS) ​

Conforme a documentação original (docs/02), o Supabase deve ter RLS habilitado por tabela, com políticas que restrinjam acesso por auth.uid(). A integração real com autenticação Supabase Auth é evolução prevista no plano de engenharia (docs/06) — hoje o app opera com credenciais anônimas configuradas manualmente.

⚡ Decisão de arquitetura: o login deve ser concentrado no Supabase Auth — ele é o hub de identidade único e oferece OAuth (Google, GitHub, etc.) que outros serviços podem consumir. Veja Autenticação & Identidade.
